## Ordem
1. Supabase local + migrations + pgTAP (testes primeiro).
2. Funções puras com Vitest: slug, cripto, sessão, allowlist, checagem de escopos.
3. Rotas de auth com o Google simulado (testes de rota do callback).
4. Aplicar no remoto pelo MCP, advisors, `schema.sql`.
5. Telas mínimas, verify, verifier.
6. Login real com o Gmail quando as credenciais do Google existirem.

## Testes que provam (critérios 8.1)
- pgTAP: `anon`/`authenticated` sem `select` em nenhuma `ag_*`; sobreposição recusada e `[)` aceita; faixa sobreposta recusada.
- Vitest (callback): e-mail fora da lista → `/entrar?erro=sem_acesso` e nada gravado; sem escopo de agenda → `erro=escopos`; primeiro login cria conta + conexão (token cifrado, sem `1//` em claro) + faixas + tipo padrão; segundo login atualiza o token e não duplica; `state` errado → `erro=falha`.
- Proxy: `/painel` sem cookie → 307 `/entrar`.

## Riscos
- `id_token`: validar com JWKS remoto em produção; nos testes, chave local injetada.
- Critério "token válido 8 dias depois": manual, registrar aqui quando conferido.

## Resultado (03/11/2026)
- Remoto: as duas migrations aplicadas pelo MCP `apply_migration` com o mesmo SQL dos arquivos (o MCP grava sua própria versão/timestamp no histórico remoto; o nome bate: `ag_schema`, `ag_logica`).
- Advisors após o DDL, filtrados a `ag_*`: só INFO `rls_enabled_no_policy` (esperado, seção 6) e INFO `unused_index` (tabelas novas). Nenhum WARN/ERROR em `ag_*`.
- `supabase/schema.sql` gerado do banco local (que só tem objetos `ag_*`).
- `npm run verify`: código 0 — pgTAP 3 arquivos/52 testes PASS, Vitest 7 arquivos/30 testes (inclui `POST /sair`), build com `/api/auth/google`, `/api/auth/google/callback`, `/entrar`, `/painel`, `/sair` e o Proxy.
- Tela `/entrar` conferida no navegador: claro/desktop e escuro/375 px, com as mensagens `sem_acesso` e `escopos`; sem erros no console.

## Divergências
- Depois do login o callback leva a `/painel` (página provisória com nome, e-mail, slug e Sair). A seção 8.1 do spec diz `/painel/tipos`, tela que nasce no 8.2; o redirect muda no 8.2.
- `erro=falha` no login usa o texto "Não consegui consultar a agenda agora. Tente de novo em instantes." da seção 15 (a seção 15 não tem texto próprio para falha de login).
- `vitest.config.mts` com `testTimeout: 20000` e `fileParallelism: false`: o Supabase local divide o Docker com outros dois projetos e a primeira chamada chegou a levar ~9 s. Nenhuma asserção foi alterada.
- `ag_fn_remarcar_reservar` recebe um 5º parâmetro `p_fuso` (a reserva nova precisa de `fuso_convidado`, NOT NULL); a seção 12 cita só os 4 primeiros.
- Enum `ag_tipo_notificacao` com `aviso_dono_remarcada` antes de `aviso_dono_cancelada` (o 7.2 lista na ordem inversa). Só estético; mudar exigiria migration nova, então fica assim.
- Acréscimos defensivos que não estão na seção 7: `ag_contas_nome_ck` (1–100, e o servidor corta o nome do Google em 100), checks de `dia_semana` 0–6, `tentativas` 0–5, `reserva_id` nulo só em `reconectar_google`, índices das FKs e de notificações pendentes, GRANT explícito a `service_role`.
- `supabase/config.toml`: desligados realtime, storage, edge runtime, analytics, Studio e Mailpit (a stack local ficou com 4 containers, ~170 MB). O Auth continua ligado: sem ele o Kong local não sobe (`HealthCheckTimeoutError`). O app não usa o Auth.
- Testes intermitentes: dentro do `npm run verify`, consultas ao Supabase local travavam ~20 s com o Docker perto do limite de memória (três stacks Supabase ao mesmo tempo). Correções de ambiente, sem tocar em asserção: `testTimeout: 20000`, espera do Supabase local no `tests/setup.ts` e stack enxuta. Depois disso, duas rodadas seguidas do verify com código 0.
- Regras de borda que o spec não define: login sem refresh token → `erro=falha`; parte local do e-mail curta demais vira `<base>-agenda`; `/` redireciona para `/painel`.
- `src/features/availability/holidays.ts` entrou só com a tabela 11.4 (códigos, nomes, padrão); o cálculo das datas fica no 8.4. Os nomes dos feriados vão para a tela no 8.3: lá passam por `copy.ts`.
- `supabase/schema.sql` traz também os `ALTER DEFAULT PRIVILEGES` genéricos do schema `public` (saem no dump; não são objetos do app).
- `src/server/db/types.ts` passa a ser gerado por `npm run db:types`, que acrescenta `import "server-only"` no topo.
- Domínio comprado durante o épico: `reuniao.app.br` (spec v0.3, 25.1). README já usa o redirect `https://reuniao.app.br/api/auth/google/callback`.
- Pendente (manual, depende das credenciais do Google): login real com o Gmail e o critério "token válido 8 dias depois".
